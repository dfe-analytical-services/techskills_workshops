Getting your team set up with Git

Your team members will need to download Git (x64) from the Software Centre - this is the Git software.

You’ll need to decide whether to host your repository on DevOps or GitHub, and everyone in your team will need to create an account on that platform:

  • Azure DevOps: Fill in the DevOps IT service request form - see the help page on how to fill in the DevOps IT request if you need support filling it in.

  • GitHub: Just create your own GitHub account, no IT support needed! You should use your work email address for GitHub accounts you will use at work.

You should then create a repository for your project:

  • Azure DevOps: It is likely your work area already has a DevOps project; if so, you should request access from the project owner. If not you can use the same IT service request form as for creating an account to create a new project. Within your area’s DevOps project, you can then create a new repo for your specific work.

  • GitHub: Contact the EES mailbox to request access to the dfe-analytical-services organisation, and to set up a new GitHub repo.

Creating your own pull request

In this example, we will mirror the changes made to one partner’s branch in the other’s branch too.

The partner who made the changes should do the following:

  1. Open the RAP for managers repo in DevOps
  2. On the left navigation bar, under “Repos”, click on “Pull requests”
  3. Click “New pull request”, select your branch (the one with the changes made to it) as the source branch, and select your partner’s branch to merge into
  4. Add your partner as a required reviewer
  5. Click “Create”

The other partner, whose branch was changed, should receive an email notification requesting their review of the code. Once satisfied the code is correct, they can “approve” and “complete” the pull request, and the changes will then be reflected in the other partner’s branch.

Expert level: Automated testing

Testing is a way to verify that your code works as intended - relevant to the verification pillar of the QA framework.

  • There is a whole range of different types of testing; see DfE’s Good Code Practice guidance for more info on testing types.
  • Testing should be automated as much as possible and should be run wherever your code has been changed; catching errors quickly makes them faster and easier to fix!
  • Expert level: Pull requests can be set up to require automated tests to pass before they can be completed.

Expert level example: Automated tests on the dfeR pretty_time() function, using the testthat package

# Test that function produces expected outputs
test_that("pretties time", {
  expect_equal(pretty_time(8), "8 seconds")
  expect_equal(pretty_time(121), "2 minutes 1 second")
  expect_equal(pretty_time(8008), "2 hours 13 minutes 28 seconds")
})

# Test that function produces error message for non-numeric input
test_that("fails if not numeric", {
  expect_error(
    pretty_time("a"),
    "Seconds must be a numeric value or vector of numeric values."
  )
})

Expert level: Branch management

To ensure you are using best practice in Git branching:

  • A new branch should be created for any updates to your code
  • Branch names should follow consistent, best practice naming conventions (more detail on the next slide!)
  • A branch should handle contained, well-defined and finite updates
  • Avoid merging branches without using pull requests
  • Branches should be deleted where they are no longer needed

Expert level: Naming branches and commit messages

You should follow consistent conventions when naming repo branches:

  • Use prefixes to group similar branches, e.g.: feature/, fix/
  • Be descriptive, summarising branch purpose, e.g.: feature/add_school_filter, fix/ethnicity_inconsistencies
  • Lower case and use hyphens or underscores, e.g.: fix/rounding_error rather than fix/RoundingError
  • Include issue or ticket numbers, e.g.: fix/issue_123
  • Be concise, e.g.: NOT feature/add_new_table_to_summarise_average_grade_by_pupil_ethnicity
  • Avoid using your name (even though we did today!)

Use these guidelines to ensure your commit messages are helpful:

  • Use the imperative tone, e.g.: Add feature rather than Adding/Added feature
  • Keep it short, limiting to 150 characters if possible
  • Explain the change and its reasoning, e.g.: Define function to calculate subject mean to improve code efficiency
  • Capitalise the first letter and don’t end with punctuation

Example: correcting filter error

# Filter out students over 18
cleaned_data <- student_data %>%
  filter(age > 18) %>%
# Calculate average score by subject for students under 18
  group_by(subject) %>%
  summarise(mean_score = mean(score), .groups = "drop")

Review Comment:

The comment on line 1 suggests that students over 18 should be filtered out, but the code filter(age > 18) keeps students over 18 instead of removing them. I think the filter condition should be filter(age <= 18).

Suggested Revision:

# Filter out students over 18
cleaned_data <- student_data %>%
  filter(age <= 18) %>%
# Calculate average score by subject for students under 18
  group_by(subject) %>%
  summarise(mean_score = mean(score), .groups = "drop")

Example: removing hard-coding

# Calculate average score by subject for 2023
average_scores <- student_data %>%
  filter(year == 2023) %>%
  group_by(subject) %>%
  summarise(mean_score = mean(score, na.rm = TRUE), .groups = "drop")

# Display a summary message for 2023
paste0("The average scores by subject for the year 2023 are as follows:")
average_scores

# Save the 2023 results to a CSV
write.csv(average_scores, "average_scores_2023.csv", row.names = FALSE)

Review Comment:

The year 2023 is hard-coded in several places. Please can you define the year as a variable at the top of the script so the code is easier to maintain in future years?

Suggested Revision:

# Define the analysis year
analysis_year <- 2023  # Update this each year

# Calculate average score by subject for the analysis year
average_scores <- student_data %>%
  filter(year == analysis_year) %>%
  group_by(subject) %>%
  summarise(mean_score = mean(score, na.rm = TRUE), .groups = "drop")

# Create a summary message for the analysis year
paste0("The average scores by subject for the year ", analysis_year, " are as follows:")
average_scores

# Save the results to a CSV
write.csv(average_scores, paste0("average_scores_", analysis_year, ".csv"), row.names = FALSE)
